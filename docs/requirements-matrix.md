# Requirements Matrix — Mini Project 08: Production Incident Triage and Runbook Assistant

Source of truth: `MiniProject_08_Incident_Triage_Runbook.pdf` (5 pages, UE24AM342AA5).
Companion documents: [architecture.md](architecture.md), [implementation-plan.md](implementation-plan.md).

**Status legend:** `NOT IMPLEMENTED` → `IN PROGRESS` → `IMPLEMENTED (unverified)` → `VERIFIED (evidence: <link>)`.
A requirement moves to `VERIFIED` only when its verification test has actually been run and the output/evidence is linked. `PARTIAL` means a named part is verified and the rest is not implemented.

**Current state (2026-10-27): Milestone 1 complete on the author's machine** — see [progress-log.md](progress-log.md). Only foundation parts of D4, F8 and D6 exist; every other requirement is not implemented.

**Priority legend**
- **P0 — critical foundation**: without it the system does not start, does not serve a valid request, or fails the zero-mark gate (§10), or it is the core of F5/F7 ("hold most of the difficulty").
- **P1 — high priority**: required for one of the ten demonstration items or a heavily assessed requirement; built after the end-to-end path works.
- **P2 — later enhancement**: deepens an implemented requirement; dropped first if time runs short.

**Note on "22 requirements" (§10).** The PDF says "Completing all 22 requirements is not expected". A1–A8 + L1–L6 + D1–D8 = 22, so the count appears to refer to the agent/LLMOps/platform requirements; F1–F8 describe what the system must do and are treated here as non-negotiable functional scope. This interpretation is an assumption to confirm with the instructor at Evaluation 1. Note also that the ten demonstration items (§9) effectively make A5, D5, D6, A7 and L4 mandatory, because each one is needed for a demo item.
